# 日志监控

## 一、定位

五层日志体系，覆盖从 API 到基础设施的全链路。

---

## 二、日志层级

| 层级 | 内容 | 示例 |
|------|------|------|
| **API 日志** | 请求/响应、耗时、状态码 | `POST /v1/chat/completions 200 1.2s` |
| **Workflow 日志** | Graph 执行流程、Node 切换 | `Node: planner → retrieve → reason` |
| **Tool 日志** | 工具调用、耗时、结果摘要 | `Qdrant.search: 10 results in 0.3s` |
| **LLM 日志** | Prompt/Completion、Token 用量 | `LLM call: 500 input tokens, 200 output tokens` |
| **Database 日志** | SQL 查询、耗时 | `SELECT * FROM documents: 50ms` |

---

## 三、日志格式

```text
2026-07-17 10:30:00 | INFO | request_id=abc123 | layer=api | POST /v1/chat/completions | status=200 | duration=1.2s
2026-07-17 10:30:00 | INFO | request_id=abc123 | layer=workflow | node=planner | started
2026-07-17 10:30:01 | INFO | request_id=abc123 | layer=tool | tool=llm | duration=0.8s | tokens=500
2026-07-17 10:30:01 | INFO | request_id=abc123 | layer=workflow | node=planner | completed | duration=1.0s
```

---

## 四、日志级别

| 级别 | 使用场景 |
|------|---------|
| DEBUG | 开发调试，State 详细内容 |
| INFO | 正常运行，关键流程节点 |
| WARNING | 可恢复异常，重试成功 |
| ERROR | 不可恢复异常，需要人工介入 |
| CRITICAL | 系统级故障，服务不可用 |

## 五、Request ID 贯穿

每个请求生成唯一 `request_id`，贯穿全链路：

```python
import uuid
from fastapi import Request

@app.middleware("http")
async def add_request_id(request: Request, call_next):
    request_id = str(uuid.uuid4())
    request.state.request_id = request_id
    response = await call_next(request)
    response.headers["X-Request-ID"] = request_id
    return response
```

## 六、Docker 日志配置

所有容器统一日志配置：

```yaml
logging:
  driver: json-file
  options:
    max-size: "50m"
    max-file: "3"
```
