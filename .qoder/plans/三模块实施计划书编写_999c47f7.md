# 三模块分步实施计划书编写

## Summary

在 `docs/design/` 下新建 3 份实施计划书。所有内容基于已完成的对齐分析（见上文 10 项分歧决策），每份包含：模块定位、与现有项目的差距、阶段划分、任务清单、依赖关系、优先级、验收标准、风险与回滚建议。不修改三份原设计文档，不改动任何代码。

## 交付文件（3 份新建 Markdown）

### 1. `docs/design/Document Pipeline + Knowledge Package 实施计划书.md`
- 定位：唯一知识生产层，输出 Knowledge Package（唯一契约），职责边界照抄 V3.0 第 1/12 节。
- 差距：现状仅 Parse→Chunk→Embedding→Index（年报）；Acquire/Routing/Publish、Package 契约、多源接入缺失；Knowledge Ingestion Agent 独立运行未编入 Stage 5。
- 阶段划分：
  - Phase A 契约先行（P0）：定义 Package JSON Schema（含 V3.0 第 7 节全部字段：Package/Source Metadata、Entities、Relations、Facts、Events、Embeddings、Evidence、Confidence、Processing Metadata、Version）+ `knowledge_packages` 幂等迁移表 + pydantic 模型。
  - Phase B Pipeline 阶段化重构（P1）：在 `pipelines/document_pipeline.py` 引入 Stage 抽象（Acquire/Routing/Parse/Chunk/Extraction/Embedding/Package/Publish 记录到 tasks.stage 与 processing metadata）；Routing 先支持 annual_report/general 两策略。
  - Phase C Extraction 编入（P1）：Knowledge Ingestion Agent 作为 Stage 5 执行器被 doc_pipeline 编排（替代现直写路径的调用入口），产出写入 Package 草稿。
  - Phase D Publish 与多源（P2）：Publish 端点写 knowledge_packages 并通知 KOC Inbox；web/news 源以 source_type 接入统一 Acquire（news 仅封装发布，不改动实时链路）。
  - Phase E Dashboard（P2）：WorkflowPage 现有任务 Tab 扩展八阶段视图与统计。
- 任务清单逐项给出涉及文件（`pipelines/document_pipeline.py`、`graphs/knowledge_graph.py`、`postgres/init/15-knowledge-package.sql` 新建、`schemas/`、`api/tasks.py` 等）、优先级与验收标准。
- 风险与回滚：契约表纯新增可回滚；Extraction 编入采用双通道开关（policy 配置），异常时回退直写路径。

### 2. `docs/design/Knowledge Operations Center 实施计划书.md`
- 定位：知识运营/治理/搜索/分析/服务（照抄 KOC 设计第 1/17/18 节），明确不做 Upload/OCR/Chunk/Embedding/Pipeline。
- 差距：core.* schema、AGE、EntityBrowser/GraphWorkspace/SemanticSearch、Inbox HITL 审核已有；Inbox 未与 Package 对接，Governance/Insights/Analytics/Evolution/Impact/Services 统计缺失；`knowledge.*` 与 `core.*` schema 双轨待收口。
- 阶段划分：
  - Phase A Inbox + Validation（P0，依赖计划书 1 的 Phase A 契约）：KOC Inbox 消费 knowledge_packages，校验→Merge→落 core.*，复用现有 KnowledgeReviewPage HITL。
  - Phase B Governance（P1）：基于 `core.knowledge_conflicts` 建冲突/重复/低置信度面板 + Review 流；`knowledge.*` schema 标记 deprecated 并出迁移脚本。
  - Phase C Explorer + Search 增强（P1）：Knowledge Explorer（按实体类型浏览/筛选/知识卡）、Hybrid Search 统一入口（现有 search/rag 合并）。
  - Phase D Analytics + Insights + Evolution（P2）：增长/覆盖率/使用量统计、趋势热点、实体时间线（audit.knowledge_versions 已备）。
  - Phase E Impact + AI Knowledge Services（P2）：AGE 图谱影响链分析、mcp-knowledge 调用统计面板。
- 风险与回滚：每阶段独立 API/组件，前端走 EmptyState 降级；schema 废弃前双读验证。

### 3. `docs/design/Agent Center 后续演进实施计划书.md`
- 定位：Agent 注册/配置/Prompt/Skill/Tool/MCP/Memory/运行记录与监控（沿用原实施计划范围）。
- 差距：P1+P2+P3-1 已落地并逐项验证（迁移、Registry、Detail、Prompt DB 化、Config、Skill/Tool/MCP/Memory、埋点归档）；剩余 P3-2~P3-5 与 Phase 4；另发现 `specs/agent-registry.yaml` 目录映射与实际代码路径不符（`langgraph/agent/*` 不存在，实际在 `graphs/`+`nodes/`）。
- 阶段划分：
  - Phase 3 收尾（P0/P1）：P3-2 Workflow 图（LangGraph 原生导出 + ReactFlow）、P3-3 Metrics（agent_runs 聚合 + providers.yaml 计价）、P3-5 Logs/Trace、P3-4 Dashboard 布局。
  - 对齐任务（P1）：修正 agent-registry.yaml 路径映射；Knowledge Ingestion / News Intelligence 两个 Pipeline Agent 纳入 Registry 与 agent_runs 口径。
  - Phase 4（P2）：热更新、Prompt 版本/审批、A/B、Marketplace、跨 Agent Trace、权限。
- 任务清单直接继承原实施计划 P3-2~P4-6 的验收标准，补充依赖关系表与既有风险表（第 4 节）。
- 风险与回滚：ReactFlow 渲染失败回退静态节点序列；Metrics 口径以 agent_runs 唯一数据源为准，禁止节点层重复埋点。

## 编写约定

- 三份计划书开头各附"对齐结论摘要"，引用统一的分歧决策表（同上表 1-10）。
- 术语统一：生产侧一律 Document Pipeline + Knowledge Package；运营侧一律 Knowledge Operations Center；"Document Lifecycle" 不再出现。
- 任务编号采用 `DP-x / KOC-x / AC-x` 前缀，便于跨文档引用依赖。
- 不新建其它文件、不修改现有设计文档与代码。

## 验收标准

- 3 份文件存在且结构完整（模块定位/差距/阶段/任务清单/依赖/优先级/验收/风险回滚八要素齐全）。
- 任务清单引用的文件路径均与代码库实际路径一致（已核对）。
- 三份计划书的依赖关系互相咬合：计划书 2 的 Phase A 显式依赖计划书 1 的 Phase A；计划书 3 的对齐任务引用计划书 1/2 的 Agent 编排变更。
- 不改变原设计方案核心目标（生产/运营/Agent 管理三分）。
